# H3 attention measurements on H100, 2026-09-14

FA4 BF16 has not shown a meaningful advantage over the current FA3 BF16 path on these H3 inputs. SageAttention2 is faster with measurable approximation error. Both tested dense FP8 paths have substantial long-sequence error; no low-precision attention backend is approved for quality-preserving serving by this experiment.

## Method

The ordinary default-home `cozy run local/h3-attention-oracle/probe` path captures post-RoPE BF16 Q/K/V from the unchanged published H3 1.14.3 graph, seed 7101, 15-second standard-30 schedule. All candidates within an arm receive the same tensors. The full shape is `[1,109104,56,128]`, dense, noncausal, with scale `1/sqrt(128)`. All reported captures so far are from denoising step 0. Model weights are the existing FP8/AdaLN-pruned checkpoint; this is distinct from the attention arithmetic being compared.

Baseline and ablation timings are medians of five synchronized CUDA-event measurements after warmup; private kernel candidates use three. Calls are measured including required quantization, smoothing, layout and BF16 output conversion. CUDA profiler traces are retained. Fidelity uses 16 evenly distributed query rows against FP32 attention over all keys/values, plus every output element against FA3 BF16. TF32 is disabled. These are sampled kernel errors, not perceptual video-quality scores. All reported candidates repeated exactly on their fixed inputs, and input fingerprints were unchanged.

FA4 required about 1.97 seconds of initial import/construction and a 1.85-second first call in the first arm. The measured image contains FA4 4.0.0b30, cuDNN backend 9.20.0.48/frontend 1.29.0, SageAttention2 2.2.0, Torch 2.13.0+cu130 and Runtime 0.17.2. This does not claim to benchmark newer cuDNN 9.24.

FA4 in this version provides BF16 on Hopper; its FP8 implementation targets SM100. Sage2 uses INT8 Q/K and FP8 P/V with its two-level accumulator; it is not a BF16 attention implementation merely because the interface accepts BF16 tensors. The cuDNN FP8 arm uses one explicit power-of-two scaling policy and Hopper FP8 output, then converts to BF16; different scaling policies remain untested.

## Isolating FP8 error

The QKV round-trip control uses exactly the production FP8 quantizer, dequantizes back to BF16, then calls FA3 BF16. Its substantially lower error separates input-quantization loss from additional loss within the FP8 attention operation. Sequence-prefix ablations retain the original 15-second Q/K/V and truncate all three tensors; they are not shorter-video benchmarks.

Explicit split-KV reduces FP8 relative L2 from 0.31196 (one split) to 0.23528 (two) and 0.16100 (four), while latency rises from 369.84 to 378.92 and 386.50 ms. Extra memory and the remaining error make this a diagnostic control, not a proposed fix. The separate-FP32 PV accumulator candidate has now completed matched 32K and full-sequence GPU tests; results follow.

## Two-level accumulator candidate

Candidate source `e4ad1ed052626bdee606345371cb9f4e376c786e` changes PV accumulation only. It runs beside the baked kernel under a unique namespace, using the same production QKV quantizer. The matched rebuilt BF16 control is byte-identical to baked BF16 at both sequence lengths. Every arm repeated exactly. The corrected FP8 output is still approximate.

| Tokens | BF16 ms | Production FP8 ms / L2 | Two-level FP8 ms / L2 | QKV round-trip L2 |
|---|---:|---|---|---:|
| 32768 | 42.65 | 33.67 / 0.17245 | 42.68 / 0.02846 | 0.02771 |
| 109104 | 508.18 | 371.00 / 0.31196 | 472.99 / 0.02690 | 0.02679 |

At full length the output-norm ratio improves from 0.77289 to 0.99772. Nearly all the excess error beyond the QKV conversion control disappears, supporting the long-accumulation diagnosis. The untuned candidate is only about 1.07x faster than BF16; compiler-reported spills motivate a separate tile-size experiment. The later-block controls below expose substantial remaining input-quantization error. The tile-size experiment below recovers part of the lost speed while retaining the quantization limit.

Later blocks of the same first denoising step:

The final block retains approximately 17.9% relative error even in the quantize/dequantize control. The accumulator correction therefore does not establish quality-preserving FP8 inference. The 2.69% first-block result must not be generalized to the whole model.

These candidate tests used H100 `GPU-d3f7b7bb-8782-5287-3439-766a4c0a6667` on owned rental nearl. Image13fd/Runtime0.17.2/TensorFS0.3.40/Torch2.13 were retained. The first request included that repair and cold setup; its 1873-second queue time is not kernel execution time.

## Smaller FP8 tile

Candidate `76aebdf701653cb41036c1523cb6c03606d22a10` changes the corrected kernel's dense FP8 tile width from 224 to 128. The separate FP32 accumulator and production quantizer remain. Reported spill stores/loads shrink from 548/424 to 16/32 bytes. Every fixed-input repetition remains identical; the rebuilt BF16 control is byte-identical to the baked implementation.

| Capture | BF16 ms | Corrected original tile ms | Corrected tile128 ms / L2 | Sage2 ms / L2 |
|---|---:|---:|---|---|
| N=32768, block 0 | 44.78 | 43.20 | 36.97 / 0.02833 | 39.00 / 0.01028 |

At full length, tile128 is approximately 1.28x faster than BF16 on the first block and 1.25x on the last. The last-block relative error remains approximately 17.9%, so these results still do not support a quality-preserving serving claim. Matched full videos are a separate ongoing experiment.
